## Security and runtime contract

- All writes require a verified admin session and the existing `content.manage`, `media.manage`, or `settings.manage` capability; the database RPC rechecks that the actor is an enabled Full Admin.
- Administrative responses are private/no-store. Browser roles receive public projections only; drafts and private settings are never returned by public reads.
- Every mutation checks its expected version and records a bounded audit event in the same SQL transaction. Client validation is usability only; SQL constraints remain authoritative.
- Demo mode continues to use the existing isolated mock store. Live mode never treats a mock mutation as saved and never falls back to sample content if Supabase is unavailable.
- No migration is auto-applied or executed against a hosted project. Hosted/local Supabase security scripts are operator checks and remain **NOT EXECUTED** until an authorized operator runs them on a disposable/local instance.

## Known live verification boundaries

A local source/test pass cannot verify the deployment's migration history, Full Admin provisioning, Storage bucket/CDN configuration, public URL availability, or a fresh-session browser reload against hosted data. These require an operator-configured disposable or approved live environment. The Phase 6 repair migration preserves the existing FAQ records and five approved `/images/GALLERY-*.jpg` placements when the durable tables are empty; newly uploaded gallery media should use the dedicated Storage bucket and HTTPS public URLs.
